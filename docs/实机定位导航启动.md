# 实机定位与导航接入框架

定位导航现已接入 `robot_bringup/robot.launch.py`，不需要单独执行 Python 文件。
全部代码在同一 `7503robot-main` 项目中；路径通过脚本所在目录解析。
**已完成的是代码接入和离线验证。尚无实物，未验证实际雷达噪声、遮挡、轮速控制和整机搬运。**

## 1. 没有实物时怎么用

继续使用已验证的仿真入口：

```bash
# 进入你电脑上的 7503robot-main 项目根目录
bash scripts/build.sh
bash scripts/run_rack_sim.sh
```

不要同时启动仿真入口和实机入口，它们都拥有 `/odom` 和导航 TF。
查看实机接入代码、运行离线测试不需要启动任何节点：

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash
python3 -m pytest -q src/robot_navigation/test
```

如要由你手动检查实机节点的启动与等待状态：

```bash
bash scripts/run_robot.sh
```

这个命令默认启动定位、雷达 costmap、导航服务和路径跟踪器，不启动状态机，也不启动 Gazebo。
`calibration_verified: false` 时不发布定位位姿，拒绝运动目标。
没有扫描/底盘跟踪服务/实测反馈时导航显示未就绪；这是预期等待，不应伪造健康状态或把标定设成 true。
Nav2 costmap 此时也会等待 TF。雷达驱动、二维码、升降和底盘节点由相应负责人提供。

## 2. 拿到实物后的配置

1. `src/robot_bringup/config/navigation_robot.yaml`：测量四壁内表面尺寸、起始位姿、雷达相对 base_link 的 x/y/z/yaw、空车和载货最大包络，确认速度与停稳阈值后才设置 `calibration_verified: true`。
2. `src/robot_bringup/config/costmap_robot.yaml`：同步 `/scan` 名称、空车足迹、雷达有效距离、地图覆盖范围。未知格按 allow_unknown_in_field 策略处理，当前允许场地内未知格通行；已探测障碍始终阻挡。载货扫掠检查由导航按载货包络独立完成；导航还按新鲜实测升降状态发布 global_costmap/footprint，用于清除自体货架腿，切换后等待新地图再接单。
3. `src/robot_bringup/config/targets_robot.yaml`：填写 START/END 前方扫码位姿、A→D 完整 QR、检查点及各自投放点；按从左到右、从里到外设置 drop_pose。ROS yaw 单位弧度，扫码角度在行进朝向上加 pi/6。
4. `src/robot_bringup/config/mission_robot.yaml`：已保留二维码/动作反馈自动推进；到放货点自动卸货、自动退出到下一检查点，最终 END 识别后停止。实机的 180 秒计时及各动作超时要与队友联调。

当前定位算法是**已知矩形场地的四壁点匹配**，要求可见足够多的两类墙面、起始估计在收敛范围内、雷达水平安装。
它不适用于任意未知场景；雷达被货物遮挡或墙面条件不满足时会拒绝更新，导航取消执行。
输入为 `sensor_msgs/msg/LaserScan`，若驱动输出 PointCloud2，先提供转换节点。
雷达外参实际参与点变换，不是只发布 TF。定位仅使用扫描数据，不输入 IMU/仿真真值。

TF 唯一发布方是本包定位节点：`map→odom` 为恒等静态关系，`odom→base_link` 为雷达实测位姿，`base_link→laser` 为配置外参。
这是当前绝对场地定位的坐标约定；禁止队友另发同一 TF 或另一个 `/odom`。
以后替换为另一套 SLAM 时，应关闭/替换本定位节点，并同时处理导航中的 map/odom 转换，不能只换话题。

## 3. 完整框架统一启动

上述配置填写完成、队友模块接好后，由操作者执行：

```bash
bash scripts/run_robot.sh start_mission:=true
```

同一入口启动定位、costmap、导航、路径跟踪器和任务状态机，真实时钟 `use_sim_time=false`。
未填写的真实目标会明确报错，禁止回退到仿真目标。实机默认不自动 arm。
队友节点、调试终端必须统一 `ROS_DOMAIN_ID=42`，使用同一 ROS 通信配置。
所有模块就绪且车已停止、平台已降下时，操作者调用：

```bash
export ROS_DOMAIN_ID=42
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 service call /team2/robot/mission/arm std_srvs/srv/Trigger '{}'
```

先到起点前方、逆时针转 30°，START QR 成功后导航会原地回正，随后平移到 A 检查点。
之后按框架状态机与 QR/动作完成结果自动搬 A→B→C→D，最终到终点前方扫码。
FINISHED 表示停止确认完成；实机进程保留供查看状态，不自动杀死队友程序。

## 4. 给底盘跟踪与整机联调同学

上游保持 `/team2/robot/navigate_to_pose`（NavigateToPose）不变。
本包规划后调用 `/team2/robot/base/track_path`（mission_interfaces/action/TrackPath）。
类型见 `src/mission_interfaces/action/TrackPath.action`，发送位置见 `src/robot_navigation/robot_navigation/navigation.py` 的 `run_track()`。
规划节点不发布速度，本包 path_tracker 服务端读取有序 map 路径和新鲜雷达位姿，闭环计算 base_link 的 vx/vy/wz 并发布 `/cmd_vel`。ESP32 的 Twist 接收、逆运动学、传输与轮速闭环由底盘同学实现。

- 平移轨迹：第一点是实测起点，后续折点只改变 x 或 y，车头固定，不能把姿态当作路径切线，也不能自行圆滑成斜走；`allow_in_place_rotation=false`。
- 原地旋转轨迹：两点位置相同、姿态为目标车头方向，`allow_in_place_rotation=true`；只在空车时出现。先回正、再平移、最后扫码旋转是独立动作，禁止边走边转。
- 单点轨迹：目标与当前位置重合，执行停稳检查；不能当非法空路径。
- 携货：`carrying=true`，严禁转向；速度、位置/航向容差、连续停稳时间均在 Goal 中，服务端还应按实物能力进一步限幅。
- Result：只在实际到位且停稳后 success=true/stopped=true，final_pose 为新鲜实测 map 位姿。失败/取消也要真实报告 stopped；取消请求应立即停止发运动指令，等待底盘停稳后返回 CANCELED 结果。ACK、发零速度、距离很小均不等于完成。
- 看见障碍、扫描/地图/反馈过期、货物状态变化、偏离轨迹或航向、超时都会取消当前跟踪。取消结果无法确认会锁定导航故障，不再派发路径；实车确认停止、检查问题后再重启导航。

`/team2/robot/navigation/path` 是相同路径的可视化副本，不可另启动一个订阅它自动驱动车轮的控制器。
底盘必须有独立命令看门狗；ROS 或上位机消失时由 ESP32 停车，不能依赖导航发最后一条零速度。
队友实现的 Dock 负责进架/退架与近距离控制；当前导航只处理检查点/投放点等普通目标，不替代 Dock、QR、升降模块。

整机健康聚合器由联调同学提供，继续发布 `/team2/robot/robot/status`（相对名 robot/status）。
把本包 `/team2/robot/navigation/status` 的新鲜 healthy 值汇入 modules.navigation；ready 单独显示当前是否允许运动。平台运动中 ready=false、healthy=true，禁止把它当断联。不新建另一个竞争发布者。
本包读取聚合器中的新鲜 modules.base/lift、measured lift_is_up、stopped 和 fault 来确认携货与底盘状况。
健康时间戳必须连续递增，使用真实 ROS 时钟；缺失/估计的升降状态不允许派发导航。
导航自身不检查聚合结果中的 modules.navigation，避免循环等待；完整任务框架仍检查全部模块。

整机 `/team2/robot/safety/stop` 服务实现方需先调用 `/team2/robot/navigation/stop`（Trigger），取消并确认旧 TrackPath 已结束，再停止 Dock、底盘并保持平台，最后依据新鲜实测反馈返回整机停止成功。
`navigation/stop` 只确认导航停止，不宣称整机、升降或 Dock 已停止。

## 6. 已加入树莓派路径跟踪器

`robot.launch.py` 已同时启动 `robot_navigation/path_tracker`，不需要队友另写 TrackPath 服务端或单独启动此文件。
默认 20Hz 用雷达位姿反馈算 `/cmd_vel`（Twist），只在执行轨迹或停止确认期间发布；闲置不持续发零，Dock 接管前必须等 TrackPath 结束。
ESP32 不读取地图路径，负责车体速度接收、麦轮逆运动学和编码器轮速闭环，仍须独立看门狗。
实机健康聚合必须报告真实轮速／平台状态，不能由跟踪器发零命令推定 stopped=true。
`base/tracking_status` 发布跟踪 ready、active、fault、reason；导航心跳失联、定位无效、载货改变或执行超时将进入停车确认，无法确认时返回 stopped=false 并锁定故障。
参数见 navigation_robot.yaml 的 tracking_*；代码见 src/robot_navigation/robot_navigation/path_tracker.py 和 tracking_control.py。
这些控制参数为离线联调模板，没有实物调参验证。

### 场地内未知格通行与固定地图（2026-10-10）

按当前任务要求，联合和实机配置默认 `allow_unknown_in_field: true`。
规划器允许配置 `field_size` 内的 255 未知格通行；254 已探测障碍仍阻挡，
车体/载货扫掠包络、5cm 物理余量和到位误差预留保持检查。
未知不等于已测量无障碍；途中扫描若发现新障碍，会取消旧轨迹、确认停车并重规划。
地图/雷达/反馈断流、位置偏差或无法确认停车仍会失败，不靠推进状态掩盖故障。

地图保留 `track_unknown_space: true`，使 255 与实际观测自由格可区分；
运动规划按上述开关处理 255，而不是把雷达测得的 254 清成零。
因此地图显示的灰色未知区域并不阻挡当前导航。
设 `allow_unknown_in_field: false` 可恢复严格已观测模式及未知边界前的分段观测停车。
此开关只改变未知格策略，不关闭定位或地图检查，不引入直线盲走控制。

global_costmap 改为固定窗口、原点 (0,0)。当前 Nav2 网格为 4×2m，
宽高按整数米向上取整覆盖 3.020×2.000m 场地；实际可行区域仍严格是
`[0,3.020]×[0,2.000]`，要求整个包络及余量在场内。
缓冲网格多出的 x=3.020～4.000m 不允许通行；地图外也不当作自由空间。
联合配置自动从场景生成，实机改场地尺寸后应同步 costmap 的整数覆盖范围。

未知目标可直接规划到达，不再仅因未知格增加中间停车点。
启动仍需有效雷达定位和一份已产生实际观测的地图；全未知/仅清除自身的初始化图
保持等待，当前包络中的未知按同一开关处理，已探测碰撞仍禁止启动。
无真实可行路线时保存 runtime_logs/navigation/blocked_*.npz，保留原始未知/障碍分类便于诊断。

### 启动时等待首份有效雷达地图

地图服务有响应、更新时间新鲜，不代表 Nav2 已执行第一次扫描更新。
导航启动就绪检查会拒绝全未知图，等待当前位置安全包络没有已探测障碍，
且包络之外也有实际观测格（排除仅清除车体自身的初始化图）。此时状态保持 IDLE，
速度不下发；首份有效地图到达后才自动进入 NAV_START，前往起点扫码位置并转向。
不靠固定延时，不关闭未知格检查，也不把暂未初始化当作“无路线”直接进入 FAULT。

首份观测确认后，合法进退架/升降足迹切换不会单独造成导航健康丢失；
运动仍实时检查完整扫掠包络，升降后仍等待足迹切换后的新地图再下发轨迹。
地图再次变成全未知或雷达/地图断流会阻止执行，不沿用旧就绪状态继续运动。


### 完整地图快照与足迹更新

实机定位导航包和联合模式读取 global_costmap/costmap_raw 的完整 nav2_msgs/Costmap，
该快照由 Nav2 加锁复制后发布。导航不再通过 GetCostmap 服务读取正在更新的缓冲区，
避免将足迹重算的中间空图误判为地图丢失；未知/障碍格及断流检查保持有效。
配置 costmap_topic 指定此输入，always_send_full_costmap=true 保证每次有完整网格。
新鲜度使用消息 header.stamp（快照发布时间），不使用本机接收时间刷新地图版本。
原有 metadata.update_time 缺省为零时内部转换成同一 header 时间，以便统一校验。
载货状态变化后仍需等新的完整快照才运输；没有快照会等待或停车，不沿用无限期旧地图。

足迹只在首次连接、实测空车/载货切换、重新连接时发布，不再不断发布相同多边形触发重膨胀。
途中“观测分段”停车是等待新扫描；直角路径换轴时还需停稳后换方向，符合轴向运动约束。
导航 status.costmap_pipeline.source=published_costmap_raw 可核对实际读图来源。

实现依据：[Nav2 Jazzy 地图发布源码](https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_costmap_2d/src/costmap_2d_publisher.cpp)
的 `prepareCostmap()` 在复制完整地图时持有更新锁；同文件的 `costmap_service_callback()`
未持有该锁，并把请求时刻写为地图更新时间。
[膨胀层源码](https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_costmap_2d/plugins/inflation_layer.cpp)
在收到足迹更新时要求重新膨胀。因此，重复发送相同足迹和轮询服务的组合存在读到重算中间数据的风险。
`run_1009_194159_6918` 记录了 A 已卸货、退出期间因 `no free observed cells` 停机，
同时雷达和底盘反馈仍新鲜；当次未保存故障地图原始数组，不能据日志断言所有格子具体是什么值。

同次运行的评估 CSV 中，A 前方的观测分段约暂停 2.3 个仿真秒，轴向拐点约暂停 0.5 秒。
这些暂停用于确认停止和等待新观测，不属于上述 `FAULT`；速度持续为零且状态进入 `STOPPING/FAULT`
则需要检查完整的 `reason` 和 `navigation_diagnostic`，不能仅看截断后的状态字符串。

此前五包离线构建成功，273 项 pytest、61 项导航 unittest 和一组 C++ 机构循环测试通过；模型 SDF 解析有效。
未由开发代理启动仿真，完整搬运流程需要操作者重新运行联合入口验证。



执行端已改为 world 支撑的 X／Y／航向关节链，平台物理举降与底盘运动解耦；不再使用逐帧 set_pose 服务。新包需要先 `bash scripts/build.sh`，联合入口和框架话题不变。树莓派实机可 `bash scripts/build.sh --robot` 跳过 Gazebo 包。详细故障来源、停止语义与验收边界见 [执行与停止契约审计](执行与停止契约审计.md)。
