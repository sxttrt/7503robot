# 定位导航与实机模块交接

本文描述分工和接口，不代表硬件模块已实现。当前 Gazebo 全流程由操作者反馈基本正常；完整实物验收尚未进行。

## 项目位置与阅读入口

交付目录只有 `7503robot-main/`，放在哪个用户目录不影响源码解析。
定位、规划与仿真代码已合并到项目内 `navigation/`，无需外部 rack_v3。
换电脑后在项目根目录执行 `bash scripts/build.sh`，重新生成该电脑的 ROS 构建输出。

先读框架 [README](../README.md) 的定位导航部分，再读本文；接口名称以 [interfaces.yaml](../src/robot_bringup/config/interfaces.yaml) 为准。

## 谁负责什么

| 模块 | 责任人 | 应交付内容 | 不应承担的工作 |
|---|---|---|---|
| 定位与导航 | 本项目定位导航负责人 | 雷达接入、外参、场地坐标、定位与速度估计、雷达 costmap、轴向规划、导航目标与结果、载货足迹 | QR 解码、电机 PWM/PID、平台电机驱动 |
| 轨迹跟踪和底盘 | 本包提供树莓派跟踪，底盘队友负责 ESP32 | path_tracker 闭环跟踪；ESP32 接收 Twist、麦轮逆运动学、编码器 PID、看门狗、限幅和故障反馈 | 二次交换地图轴、直接以 PWM 解释 m/s、重复发布定位 odom |
| QR 识别 | 视觉队友 | 完整二维码结果、图像时间戳、相机/识别健康 | 直接改状态机或给底盘发速度 |
| 平台举降 | 升降队友 | SetBool 完成服务、真实到位测量、停止时保持、健康反馈 | 收到命令就返回完成、固定延时猜完成 |
| 状态机与整机联调 | 框架/联调队友 | 配置、arm/stop、串行控制权、健康汇总、故障处理、端到端验收 | 把定位、电机或 QR 算法写进状态迁移 |
| 进架/退架 | 联调组与导航、底盘共同确认 | Dock 服务端、实际机械对准条件、退出完成反馈 | 将二维码识别当成机械对准已完成 |

导航负责检查实际导航结果，不能把轨迹已经发给队友当作到达。Dock 的最终负责人需要团队登记；接口已经确定，不需要修改主状态机。

## 定位导航接实物要改哪些

不是只换点云源。当前算法输入是二维 `sensor_msgs/LaserScan` 的 `/scan`，不是 `PointCloud2`。若实际雷达输出 PointCloud2，应先由雷达/定位组转换到有效扫描平面；必须保留测量时间、角度方向、距离单位和传感器 frame，不能用接收时间冒充采集时间。

定位导航负责人需要完成：

1. 真实雷达驱动发布 `/scan`，`header.frame_id=laser`，角度 rad、距离 m，ROS 时间戳与整机时钟一致。
2. 实测 `base_link→laser` 安装位置和朝向。localization.py 已通过 laser_pose 把雷达平面点变换到 base_link 后再拟合；实际 x/y/z/yaw 必须测量填入，不能沿用仿真的零偏移。TF 与拟合使用同一外参。
3. 实测场地墙面、长宽、起点与机器人初始航向。当前定位依赖四面固定墙和已知初始姿态；遮挡、非矩形场地或墙面回波不足会失效，不能当作通用未知场地 SLAM。
4. 填实机目标和完整 QR：[targets_robot.yaml](../src/robot_bringup/config/targets_robot.yaml)。货架几何、车体/货物足迹、进架与退架距离也要按实测配置，不能直接复制仿真数字。
5. 确认 ROS 航向：base_link 的 +x 为车头、+y 为左，逆时针为正；出生面对场地 -x 时 yaw=π。scene.py 中图纸 yaw=0 是描述用约定，不能发送给 ROS 后再人为加/减 180°。
6. 上位机使用真实时间（use_sim_time=false）。各模块 ROS_DOMAIN_ID/RMW/发现配置一致，跨主机时校准时钟。
7. 去掉 Gazebo 执行依赖，接真实模块状态。`framework_execution.py` 当前是仿真复合执行桥，不是换 `/scan` 后即可原样部署的实机执行节点。

已知矩形场地墙匹配模式的定位输出在场地坐标中，导航 TF 是 `map→odom→base_link→laser`，map→odom 固定恒等。若后来采用另一种实机地图定位算法，由它提供 map→odom，并关闭此模式的静态发布者。SLAM 当前仅建图，不再提供导航 TF。

## 实机接口总表

框架相对名称由 `/team2/robot` 命名空间展开；下列全局定位/底盘话题不随前缀变化。

| 完整实机接口 | ROS 类型 | 提供者 → 使用者 | 成功/数据含义 |
|---|---|---|---|
| `/scan` | `sensor_msgs/msg/LaserScan` | 雷达 → 定位、costmap | 真实采集扫描 |
| `/odom` | `nav_msgs/msg/Odometry` | 定位 → 跟踪器、健康汇总 | header=odom、child=base_link；位置 m，航向 rad，twist 为车体系 |
| `/team2/robot/navigate_to_pose` | `nav2_msgs/action/NavigateToPose` | 导航服务端 ← 状态机 | map 中目标；到位停稳才成功；取消须停车 |
| `/team2/robot/navigation/path` | `nav_msgs/msg/Path` | 导航 → 显示/观察 | map 中有序路径；只是发布话题，不带执行完成握手 |
| `/team2/robot/base/track_path` | `mission_interfaces/action/TrackPath` | 底盘上位机跟踪器 ← 导航 | 导航客户端已接入实机；TrackPath 服务端由本包实现，ESP32 通信与伺服由队友实现，仿真保持原执行链 |
| `/cmd_vel` | `geometry_msgs/msg/Twist` | 唯一当前跟踪器/Dock → 底盘驱动 | 车体 vx、vy m/s；wz rad/s |
| `/team2/robot/docking/execute` | `mission_interfaces/action/Dock` | Dock 服务端 ← 状态机 | ENTER 对准并进架；EXIT 脱离货架；实际完成结果 |
| `/team2/robot/qr/detections` | `std_msgs/msg/String` | 视觉 → QR adapter | 带实际图像时间戳的完整 QR JSON |
| `/team2/robot/lift/set_up` | `std_srvs/srv/SetBool` | 平台 ← 状态机 | true 升、false 降；完成后返回 success |
| `/team2/robot/lift/is_up` | `std_msgs/msg/Bool` | 平台 → 显示 | 参考，不能单独作为完成依据 |
| `/team2/robot/robot/status` | `std_msgs/msg/String` | 健康汇总 → 状态机 | 真实模块健康、停止状态及平台完成测量 |
| `/team2/robot/safety/stop` | `std_srvs/srv/Trigger` | 停止协调器 ← 状态机 | 停车、旧操作结束、平台保持；实际完成后成功 |
| `/team2/robot/mission/arm` | `std_srvs/srv/Trigger` | 状态机 ← 操作者 | 实机显式启动；就绪前拒绝 |
| `/team2/robot/mission/stop` | `std_srvs/srv/Trigger` | 状态机 ← 操作者 | 发起受控停止 |
| `/team2/robot/mission/status` | `std_msgs/msg/String` | 状态机 → 各组 | 状态、当前货架、原因、诊断；不是控制命令 |

`/team2/robot/robot/status` 中两个 robot 是命名空间 robot 与相对名 robot/status 拼接的结果，是当前配置的实际接口名，不要自行缩成 `/team2/robot/status`。更名应同时修改 interfaces.yaml 和所有发布者。

## 底盘队友如何接轨迹与 ESP32

当前仿真：导航 `drive_seg()` 自己跟踪路径，发布 `/cmd_vel`，kinematic_driver 执行。因此只负责 ESP32 四轮伺服时，订阅 Twist 即可，不要再跟踪 Path。

当前树莓派上位机跟踪已使用 [TrackPath.action](../src/mission_interfaces/action/TrackPath.action)：导航规划 map 路径，发送 TrackPath，本包 path_tracker 根据雷达位姿闭环跟踪并发布 `/cmd_vel`，队友负责 ESP32 端执行。导航等待实际执行结果，再完成 NavigateToPose。实机委托已在 robot_navigation 中实现；实机入口不启动 drive_seg() 或仿真驱动，TrackPath 服务端由本包实现，ESP32 通信与伺服由队友实现。不能同时运行两套跟踪器。

TrackPath 的约束：

- path 必须非空，所有 PoseStamped 与 Path 都在 map；第一点是规划时的实测起点，相邻点只允许一条场地轴发生变化。姿态是车体姿态，不是路径切线方向。
- 到位必须使用实测定位和停稳反馈，结果里的 stopped=true 不是“已发零速度”。结果 success=true 要同时符合最终位置、航向、速度及规定停稳时长。
- 空载起终点可以原地回正或左转30°，allow_in_place_rotation 控制许可；载货 carrying=true 时禁止旋转。不得边平移边转向或斜走。
- 参数单位均写在 action 注释中；跟踪器按实测底盘能力限幅，不能默认所有仿真数值适用于实机。
- 动作取消/超时/定位失效应立即撤销旧速度，停车并给出最终结果；新目标不能与旧目标并行。导航发现新障碍，应取消旧路径并确认停止后重规划。
- TrackPath 未定义无地图进架权限。Dock 的 ENTER/EXIT 使用独立机械对准逻辑；不应让普通导航路径绕过地图检查。

ESP32 执行的是车体系速度：linear.x=前后、linear.y=左右、angular.z=旋转；不把地图坐标直接写成轮速。树莓派与 ESP32 可采用 micro-ROS 或有明确定义的串口协议，实际传输方案由底盘组交付，当前未实现串口帧或烧录程序。

轮速闭环、X型麦轮公式、轮序与参数见 README 的底盘章节。命令周期、超时停车、编码器反馈、故障与急停由底盘组实现。`/base/wheel_states` 是待实现的反馈建议，不是当前已存在的节点；轮速反馈不得重复发布雷达所有的 `/odom`。

## QR 与平台的交接样例

视觉发布 `std_msgs/String.data`，以下仅为结构，时间戳必须取本次真实图像：

```json
{"image_stamp":{"sec":1791470000,"nanosec":100000000},"status":"ok","detections":[{"raw":"RACKA_XXXX"}]}
```

START/END 使用相同结构，raw=START/END。货架完整码以实机目标配置为准。当前单条上游已确认结果即可推进；不再发 /rack/next。读 [qr.py](../src/mission_manager/mission_manager/adapters/qr.py) 查看窗口、时效和去重检查。

平台接收 SetBool 后驱动真实升降并等待到位。举升到位才返回 success=true；下降必须确认到位和载荷释放。随后健康汇总发出本次请求之后的新鲜 lift_is_up 与 lift_state_source=measured。Bool 显示话题、已收到命令或上一动作的稳定状态均不能代替本次完成。读 [lift.py](../src/mission_manager/mission_manager/adapters/lift.py)。

健康 JSON 示例：以下 stamp 为结构示例，必须换成当前测量时间；modules 根据真实状态填写，不能固定 true。

```json
{
  "schema_version":1,
  "stamp":{"sec":1791470000,"nanosec":100000000},
  "modules":{"navigation":true,"qr":true,"docking":true,"lift":true,"base":true},
  "stopped":true,
  "base_motion_stopped":true,
  "lift_motion_stopped":true,
  "lift_is_up":false,
  "lift_settled":true,
  "lift_state_source":"measured",
  "fault":""
}
```

动作进行中/未知平台位置时 lift_is_up 应为 null；只有实际停稳时 stopped=true。健康汇总应使用各模块实测反馈，不能仅将收到的命令回显成完成。读 [safety.py](../src/mission_manager/mission_manager/adapters/safety.py) 的健康、停止握手检查。

## 状态机联调与替换清单

状态机队友维护 [state_machine.py](../src/mission_manager/mission_manager/state_machine.py)；算法通过 adapter 接入，禁止在状态迁移里加入 Gazebo 真值或电机控制。

当前仿真流程是 NAV_START→WAIT_START→NAV_RACK→WAIT_RACK_QR→DOCK_ENTER→LIFT_UP→NAV_END→LIFT_DOWN→DOCK_EXIT；ABCD 完成后 NAV_FINAL→WAIT_FINAL_QR→STOPPING→FINISHED。QR 成功推进识别阶段，导航/Dock/举升的实际完成结果推进动作阶段，无额外 /rack/next 等待。

实机 [robot.launch.py](../src/robot_bringup/launch/robot.launch.py) 已启动雷达定位、costmap 和导航委托，默认 domain_id=42、use_sim_time=false。`start_mission:=true` 加上任务状态机，auto_arm=false。不会启动 Gazebo、真实雷达驱动、视觉、底盘、Dock、举升或健康汇总。targets_robot.yaml 仍有 null，必须现场填写完整扫码/检查点/投放点和 QR；navigation_robot.yaml 默认未确认标定，不允许运动。实机使用独立 mission_robot.yaml，与原 mock 的 mission.yaml 分开；完整步骤见 [实机定位导航启动](实机定位导航启动.md)。

替换模块时先关闭同名仿真服务/速度发布者，再启动真实模块；整机统一通信域与时间。调用 mission/arm 前核对所有必需模块就绪，停止测试同时观察新鲜 stopped 反馈和旧动作已结束。

现场验收顺序：雷达与外参→静止/轴向运动定位→空载速度与看门狗→短路径跟踪和取消→平台单独到位及保持→QR观察窗口→进退架→空载完整状态机→载货流程。每一步失败时保留日志和真实测量，不用固定延时替代完成条件。

### 导航健康与升降过程

navigation/status 的 healthy 表示定位、地图、模块反馈和跟踪接口仍正常；ready 表示当前平台状态允许导航。
升降过程中正常发送 lift_is_up=null、lift_settled=false、lift_state_source=measured，
modules.lift/base 仍按通信/实测反馈是否正常填写，而非按是否到位填写。
此时导航 healthy=true、ready=false：健康汇总的 modules.navigation 取 healthy，
navigation_ready 单独显示允许运动状态，禁止把 ready=false 当成断联。
定位/地图断流、机构报告故障仍令 healthy=false；不跳过任何数据新鲜度或故障检查。

导航与跟踪接收运动仍要求新鲜、已确认的布尔 lift_is_up；机构状态未确认时不下发运动。
升降完成后仍需服务完成响应及请求之后的实测到位状态，载货足迹切换后还要等新地图。
lift_settled 为可选布尔字段；旧接口只发 lift_is_up=null 也表示未确认，不视为动作完成。


### 停止测量与动作交接

`stopped=true` 表示底盘和升降均已实际停止，不要求机构必须位于 UP／DOWN 端点。
新汇总模块应明确提供 `base_motion_stopped` 和 `lift_motion_stopped`，取当前编码器／关节速度测量，
配合新鲜时间戳及 `lift_state_source=measured`。这两个字段不能回显零命令，也不能使用旧数据。
取消后保持当前平台位置，货物状态可为未知，但必须独立确认底盘和平台速度已停止。
Safety 最终确认仍要求服务成功、请求后的新测量和旧动作已结束；故障会禁止再次派发运动。
未提供独立测量字段的旧模块保留原先 healthy＋stopped 的停止确认。

导航请求与 Dock 完成话题不同步：导航接到合法目标后等待新的实测停稳样本，再向跟踪器发送路径，
不依赖某一次收到的旧 stopped 值，也不会通过发送速度来抢正在执行的 Dock。


### 当前未知空间策略（2026-10-10）

联合/实机默认 allow_unknown_in_field=true：场地内 255 未知格允许规划通行，254 实测障碍仍阻挡。网格固定覆盖整个场地，可行区域受 field_size 与完整包络约束；地图外不可通行。地图保留未知标记用于诊断，不再因未知目标进行观测分段。真实新障碍仍触发取消、停车确认与重规划。细节见 [实机定位导航启动](实机定位导航启动.md#场地内未知格通行与固定地图2026-10-10)。
