## 修复的代码缺陷

| 缺陷与触发条件 | 修复及回归证据 |
| --- | --- |
| 一帧未来时间或错误 frame 的扫描先推进时间戳，后续正常扫描被永久拒收 | 成功校验和匹配后才提交扫描水位；拒收后下一帧可恢复 |
| LaserScan 头被赋给 odom 后修改原消息；无效角度步长/量程未显式拒收 | 深拷贝头；校验有限角度、非零步长和合法量程 |
| JSON 时间戳的小数秒或负纳秒可替换健康缓存 | 统一严格验证 ROS Time，拒绝后不推进缓存时间戳 |
| 等待停车后扫描时把健康心跳发布时间当采集时间 | 使用实际匹配 LaserScan 保留在 odom 中的时间；心跳前进而无新扫描时保持等待 |
| 上条命令为零，但车辆仍滑行时可以换轴；过冲后可直接反向 | 同时检查实测车体速度转换的地图速度，换轴与反向先归零，等实际停止 |
| 底盘不动/持续往复仍能一直输出速度到完整动作超时 | 实测目标距离/角度的进展监测，默认 8 秒无至少 5mm/0.02rad 进展即进入停车确认；每段独立基线 |
| 升降响应成功，布尔到位字段未清除而 lift_settled=false 时可完成 | 提供 lift_settled 时必须 true；arm 也拒绝明确未停稳平台。旧发送端仍遵守响应表示实际完成的原契约 |
| 已接受动作的结果通道异常被当作动作空闲 | 报错但保留未确认动作，禁止移交；迟到终态清理但不重复推进状态机 |
| 导航默认信号先关闭 rcl；跟踪器先关闭 executor，无法处理停车反馈 | SIGINT/SIGTERM 只请求退出；保持上下文与回调运行，在有限时间内取消并接收停车结果，再关闭 |
| 非有限地图原点进入几何计算可能抛异常；缓存水位可能推进 | 在缓存入口拒绝非有限/非轴向/非归一化原点，几何层也检查有限尺寸 |
| 配置改了 navigation/status 或 navigation/stop，导航服务端仍用硬编码名称 | 发布者与服务端读取同一 interfaces.yaml，扩展名称按相对接口校验 |
| 文档同时要求用 healthy 和 ready 汇总模块健康，可导致升降中整机误报故障 | 统一 modules.navigation 取新鲜 healthy；ready 表示平台状态允许新运动，独立显示 |
| 底盘测试收到未来 odom 后后续记录不能恢复 | 可选 odom 同样先验证源时间新鲜度再更新观察缓存 |

接口类型、框架状态顺序、ABCD 顺序、普通导航必须看图、空载原地旋转/平移串行及载货禁止旋转均保持原约定。实机 calibration_verified 仍为 false、目标仍为 null，等待现场测量；未伪造硬件或健康反馈。

## 验证

29 项新增硬件边界回归，加上现有测试：343 项 pytest、61 项导航 unittest，共 404 项 Python 离线测试通过。新增测试含未来扫描恢复、消息不被修改、坏数据拒收、滑行换轴、反向停车、卡死检测、心跳不能冒充采集时间、升降未停稳、动作通道断联和退出等待。跟踪测试采用 10Hz 雷达/20Hz 控制、0.3mm 周期噪声及 0.08/0.25/0.40 秒一阶惯性模型，均能完成直角路线且命令保持单轴；这些模型没有代替实际电机、侧滑或雷达噪声。

离线命令（项目根目录）：

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash

python3 -m unittest discover -s navigation/tests -q

```

四个实机 ROS 包通过 `build.sh --robot` 重新构建；既有 C++ 四架机构循环测试通过。离线求值验证了实机 namespace、Nav2 参数根、地图/足迹/定位话题全名及安装的入口，没有执行 launch。README 本地链接和代码入口检查通过。

test_ros_integration.py 会启动节点，本次明确未运行。普通仿真/联合仿真也未重新运行；之前的顺畅运行日志对应本轮修改前版本，不能当作本轮端到端验收。

## 实物仍需要验证的边界

1. **定位可观测性**：当前是已测矩形四壁匹配，需要两类可见墙面、水平外参与足够近的初始估计。不能保证无墙、强遮挡、反光或运动畸变下连续定位；算法仍无逐射线运动补偿。静止、平移、转动、载货都须实测位姿与速度噪声，不能直接把仿真的毫米误差外推到实物。
地图 header 时间是完整快照发布时间，不是处理某一帧扫描的回执；停车后等待真实新扫描以及之后的地图发布，仍不宣称两个异步节点对扫描版本有严格一一绑定。

2. **保持航向**：平移与载货时 wz=0；偏航超过 0.04rad 会停车。ESP32/底盘需能保持车头，实际麦轮侧滑、轮径/轮距误差不在仿真理想模型内。不能通过放宽航向阈值掩盖偏航。
3. **制动和延迟**：tracking_linear_acceleration 是命令加速参数，不是实测物理制动能力。5cm 静态余量不保证突然出现的障碍可在雷达、2Hz 地图、通信和实际制动延迟内避开；先测空载/满载速度响应、停距和断流停机，再共同确定速度、余量与本地保护。
4. **实测反馈和控制权**：ESP32 通信/轮速 PID、Dock、平台、QR、robot/status 和 safety/stop 的真实实现尚未交付。它们必须提供新鲜测量和真实完成语义，不可用接收 ACK 或命令回显推定停稳；同一时刻只有一个速度控制者。上位机 SIGKILL/掉电不可能补发零，由底盘独立看门狗处理。
5. **性能与时间预算**：WSL 离线测试不证明树莓派实时调度。需记录源扫描时间、地图版本、发布/接收速度、编码器和任务状态；验证满载遮挡时处理延迟。实机每段 NAV_* 初值 30 秒、总比赛 180 秒，路线、QR 等待与停车时间需实测确认，不能凭仿真自动放宽比赛策略。

**结论：已复现的缺陷已修复并有回归证据；无实物时无法宣称所有 bug 已消失或实机流程已验收。**
