# 主状态机代码审查与修复说明（自己看）

审查日期：2026 年 10 月 8 日。基于原 GitHub 版本 `8a978ac9d819753419d5a87465fdd49ae7cb5c63`，检查主流程、异步接口、取消、停止、时间戳、升降状态及程序退出。

## 直观理解这次修改

正常搬运顺序仍是 A→B→C→D。这次主要补强每一步的交接检查。

| 情况 | 原实现的薄弱点 | 修改后的处理 |
|---|---|---|
| 导航或对准模块说“完成了” | 客户端收到成功结果即可推进，缺少独立的结果后静止核对 | 必须再收到结果接收之后生成的健康状态，确认实际静止，才开始下一步 |
| 升降说“升好了” | 可以使用请求开始之后、成功响应之前的状态，存在跨连接乱序窗口 | 等待成功响应接收之后生成的新鲜到位反馈，且方向与请求一致 |
| 搬运途中机构意外落下 | 到位检查集中在升降步骤，运输阶段缺少持续一致性检查 | 空载和运输阶段持续核对机构；意外变化时把货物状态改为 UNKNOWN 并停止 |
| 结果、发送或取消发生通信异常 | 某些异常分支会清除请求记录；但没有回报不代表动作停止 | 保留未确认请求，禁止新旧动作重叠；确认不了停止就故障退出 |
| 健康状态在网络中延迟 | 只检查收到消息后的时间，可能额外沿用已经老化的状态 | 同时检查源时间和接收时间；重复及非法消息不刷新有效状态 |
| 日志写入、状态发布或 ROS 回调异常 | 异常可能打断调度或退出路径，停止逻辑执行不完整 | 记录致命原因、撤销重试、请求停止；正常信号退出先走停止握手 |
| 已经故障停机，随后比赛时间到 | 时间到可能把待停止的故障终态改成 FINISHED | 保留 FAULT 或人工停止的 STOPPED；时间到只取消尚未执行的重试 |
| 状态记录耗时或状态在交接时变化 | 本轮早先检查通过，不代表真正发命令时仍符合条件 | 每次发出新动作前再检查比赛时间、步骤时限、健康状态和机构状态 |
| 接口名称或调度周期填错 | 部分错误直到创建 ROS 接口才暴露；周期未约束停止和健康时限 | 启动时拒绝非法名称、导航与对准同名、调度周期不短于安全时限等配置 |

例如，导航说“我到 A 了”只是第一道确认。主程序还要收到一条新状态，确认机器人真的停稳，才交给扫码或对准模块。如果一直停不稳，就等待到超时并请求停止。

## 哪些文件改了

- `state_machine.py`：持续核对机构、交接前再检查条件、异常停机、保留终态原因。
- `mission_node.py`：接入新增检查，处理主循环异常及退出停止握手。
- `adapters/navigation.py`、`docking.py`：成功结果之后的静止确认及未结束动作跟踪。
- `adapters/lift.py`：升降响应之后的新鲜到位确认、保留未确认服务请求。
- `adapters/safety.py`：严格健康数据类型、源时间与接收时间双重过期检查、故障时仍可确认实际静止。
- `config_loader.py`：提前检查接口名称和调度周期等错误配置。
- 测试及模拟场景：增加通信异常、乱序反馈、实际仍在运动、意外落下、模块故障和程序退出测试。

这里的 `adapters` 仍然是主程序调用其他模块的客户端。修改没有代替队友实现导航、视觉、底盘和升降算法。

## 队友接入时需要注意

接口名称和 ROS 消息类型保持原约定。完成条件更严格：执行模块必须持续发布真实健康状态，成功后还需要新鲜静止／到位反馈。一次性发布完成状态、只回复“命令已收到”，都不足以推进任务。

聚合状态中的 `stopped` 必须反映底盘、局部对准及升降等执行机构均已停止运动；托举保持可以继续工作。停止服务要协调各模块，旧 Action／升降服务请求还要最终结束。不要把“发了零速度”或“取消请求已经收到”当作完成。

主程序使用升降到位反馈核对携货记录，不能据此证明货架确实被托住；是否托住、是否碰撞、搬运是否触地仍需要机构和真实执行模块验证。

模拟通信域从 202 改为 62，集成测试从 197 改为 63，实机仍为 42。树莓派临时端口范围现场读取为 `32768–60999`，新默认值符合 [ROS 官方建议](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Concepts/Intermediate/About-Domain-ID.rst)。查看模拟状态的终端也要改用 62。

## 第二轮审查后的七项修复

本轮基线：`58a85e6c3f70f8d9c4679a94c35a616aec29739f`。所有修复先在独立工作区验证，保留修改前备份。

| 问题 | 本轮处理 |
|---|---|
| 故障终态再次人工停止，只回复已请求而不发命令 | 区分人工重发与退出循环检查；终态可重新确认物理停止，保留原结果、不重新启用任务 |
| STOPPING 的同步日志可能延迟停止命令 | 先设置状态并发出停止，再记录和发布，停止时限不依靠日志完成才开始 |
| 等待 QR 和下一动作前缺少静止检查 | 扫码等待持续检查；交接前再次检查；升降完成也需响应之后的新鲜静止反馈 |
| 退出或人工停止覆盖原有模块故障 | 保留原故障及原因；人工操作只撤销待重试计划，不把故障改成 STOPPED |
| 停机中不核对携货记录 | 停机及结束后也读取有效升降观察；意外变化改为 UNKNOWN、撤销重试，不从单个采样恢复 |
| 配置允许不同接口重名，物理停止可指向自身 | 全部配置端点检查互斥，同时保留 mission/arm、mission/stop 控制名称 |
| 模拟升降正在动作仍报告已停止 | 升降计入运动数量，成功、失败、中止、退出和异常路径均正确释放；退出不伪造升降成功 |

以上使用现有标准反馈字段，没有增加队友必须实现的错误码或消息类型。新增的方法属于主程序内部后端。模拟场景中的故障开关只用于回归测试，不是实机模块的接口要求。

新增回归测试覆盖终态再次停止、旧停止回调、退出检查幂等性、慢日志、扫码期间意外运动、交接时状态变化、停机期间机构变化、端点冲突，以及模拟升降的五种退出路径。新增 ROS 场景覆盖 END 扫码时仍在运动、停机期间机构下降、故障后人工再次停止和故障停机期间退出。

## 第三轮：四项结束与停止边界修复

基线为 `0410b14030b2cd26aff51910b67b75a6d9a9694f`，源自补充审查中受控复现的四项问题。

| 问题 | 修复结果 |
|---|---|
| 停止失败进入 FAULT 后退出，跳过停止确认 | 退出入口单独检查最新停止结果；未确认时补发一次有时限的停止。退出定时器不重发、不重置时限，保留原故障 |
| 终态不继续检查新运动 | 已确认静止后继续监督新鲜静止反馈；新运动或反馈失效重新停机并故障。新握手失败或超时后不无限自动重发 |
| 停止之后旧升降命令仍可执行 | 增加 SetLift 服务定义，请求携带编号、安全令牌和方向；控制器启动及每次停止更换令牌。旧、重复或重叠请求在驱动之前拒绝 |
| 重复停止成功仍只显示原停止失败原因 | 任务 reason 保留原故障；新增 stop.status、停止编号和说明，独立记录最近一次握手结果 |

### 为什么需要升级升降接口

原 SetBool 只有方向。仅在服务端检查一个停止标志，或只忽略客户端旧回调，都无法区分停止后才到达的旧命令。当前 SetLift 用安全令牌标识有效控制周期：停止使旧令牌失效，新任务复制最新令牌。正常导航／扫码重试之后的合法升降仍能工作，不需要额外复位服务。

真实升降模块必须实现同样的令牌检查及互斥规则，不能只在模拟端拒绝旧请求。聚合健康状态升级为版本 2，增加 lift_safety_token；主程序拒绝旧版健康消息。主任务状态自身仍为版本 1，stop 是新增字段。

### 新增验证

逻辑与接口测试覆盖退出补发成功、失败及超时、已确认停止不重复补发、三个终态的运动监督、重停失败不无限重发、最新停止结果与原故障分开、旧及重复升降请求、控制器重启令牌变更、缺失令牌、响应编号错误、动作期间令牌失效，以及停止确认等待新令牌。

ROS 场景新增完成四货架后再次运动、首次停止失败后通过 SIGTERM 退出并重新确认，以及升降请求延迟到停机之后才处理。最终合并结果记录在 [构建验证记录](构建验证记录（自己看）.md)。


## 按用户要求简化接口（2026 年 10 月 8 日）

- 恢复升降 SetBool，移除新增 SetLift 定义、安全令牌及去重规则；请求关联只在客户端内部自动维护。
- 健康消息只保留 ready／fault，用接收时间做断联检测，不要求版本、源时间戳、五模块明细、静止、升降位置或测量来源。
- 导航、对准、升降完成后直接使用结果，不做第二次状态核验。Dock 旧的 ready_to_lift／exited 字段仅保留兼容，不强制校验。
- 目标区导航成功直接放下，默认 confirm_end_qr=false；可选 END 路径保留。
- 执行端停止成功即完成停止等待，不等待令牌变化、新鲜静止或旧动作最终回执。仍取消旧 Action，内部编号过滤旧结果，迟到接受仍发取消。
- 保留固定顺序、三分钟、超时、有限重试、错误报告、日志及有时限的退出停止；终态不再监督静止或测量变化。
- 新版信任模块完成语义；取消令牌后不保证识别所有停止后晚到的旧升降服务请求。这是用户明确选择的接口简化，不再宣称旧版能力。

测试移除只针对已取消的契约，并补充直接完成、简易在线、SetBool、无 END 默认流程、停止成功后旧结果过滤等验证。历史测试数量不能作为新版本验证结果。


## 点位名称导航（2026 年 10 月 8 日，当前版本）

按用户要求，主程序只发送 A/B/C/D/DROP_OFF；新动作 NavigateToPoint 的请求只有 target_id，结果 success/message，反馈 phase。去货架和放置区的具体地图、坐标、朝向、规划由导航模块实现。目标配置只保留 QR 和模拟标志，不再要求坐标。

主程序仍串联导航、扫码、进入、升起、运输、放下和退出，并负责顺序、计时、超时与有限重试。导航点位动作仍支持标准取消，不新增安全令牌或二次到点确认。停止及 SetBool 升降接口不变。

测试新增完整一轮点位命令顺序、五种请求只含 target_id、真实配置无需导航坐标、点位结果的最终状态与未知点位拒绝。旧 NavigateToPose 接口改为本项目自定义点位接口；队友内部可自行使用 Nav2，不要求状态机依赖 Nav2。
