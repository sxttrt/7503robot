# 执行与停止契约审计

本次依据 `navigation/log/run_1009_201338_7887` 与对应任务转换日志审计。B 的故障发生在
`NAV_END → LIFT_DOWN`，尚未进入 `DOCK_EXIT`。驱动记录要求底盘 z=0，实际 z=0.0262792689；
X、Y、yaw 匹配，但位姿响应超时且高度无法确认，随后举降失败、停止失败。
同次 A 退出后，第一条 B 导航目标因动作结果与旧健康样本交接而被拒绝，停止重试后才继续。

## 本次查明的结构问题

| 问题 | 旧实现的触发条件 | 当前处理 |
|---|---|---|
| 自由底盘与物理举升互相影响 | 无重力不等于固定高度，lift_joint 反力推动自由底盘，set_pose 再拉回，回执判定要求 z=0 | world→X→Y→yaw→base_link 的约束链；Z／roll／pitch 没有自由度，lift_joint 保留真实物理 PID |
| 将 Gazebo 位姿服务当成逐帧执行总线 | ROS/Gazebo 服务排队、响应超时与物理积分同时发生，服务 ACK 和反馈混合决定继续积分 | 删除底盘和货架逐帧位姿服务链；Gazebo PreUpdate 每步执行关节速度、按步移动运动学货架 |
| 货物与底盘状态分散维护 | ROS 积分、服务回调、物理关节测量、缓存货物姿态分别修改 engaged／carrying／settled | Payload 状态只由 Gazebo 仿真线程维护；PostUpdate 采样后的物理位置和速度决定完成 |
| 将“未准备好”当成“无法停车” | nav/跟踪/外围桥/Safety 各层将 lift_unknown、fault 或模块健康作为停止判定前提 | 运动接收仍严格检查健康和平台状态；停止使用请求后新鲜实测底盘／关节速度，旧操作必须结束 |
| 退架完成后立即读取旧 stopped 样本 | Dock 动作结果与健康话题独立传输，下一合法导航被误拒绝 | NavigateToPose 接单后等待新的多帧实测停稳样本，再派发 TrackPath，不靠固定延时或提前发送速度 |
| 停止失败覆盖原始原因 | 最终 FAULT 只留下“停止失败”，最先失败的执行动作原因丢失 | 最终原因保留原始执行错误；实测停止成功仍不允许故障模块自动重试 |

Gazebo 8 的 [Physics 系统源码](https://github.com/gazebosim/gz-sim/blob/gz-sim8/src/systems/physics/Physics.cc)
区分关节速度命令与模型位姿命令；
[JointController 源码](https://github.com/gazebosim/gz-sim/blob/gz-sim8/src/systems/joint_controller/JointController.cc)
采用 `JointVelocityCmd` 按步驱动关节。本项目采用同一命令机制，并额外加入进程丢失看门狗。

## 数据与控制归属

```text
MS200 模拟扫描 → /scan → 实机 localization → /odom、导航 TF
 → 完整 costmap_raw → navigation → TrackPath → path_tracker → /cmd_vel
 → ROS driver（雷达/执行反馈新鲜度＋命令看门狗）
 → /simulation/chassis_cmd → Gazebo 平面执行插件（独立看门狗）

框架 lift/set_up → /lift_cmd → Gazebo 插件验证目标
 → 私有 /simulation/lift_setpoint → 物理 JointPositionController
 → 仿真内关节位置/速度和货架实际姿态 → /simulation/actuator/status
 → driver payload_status → 外围健康汇总、升降完成判定与停止协调

私有 /simulation/robot_pose → 独立误差评估；不进入导航定位
```

`/simulation/*` 是仿真内部接口，实机使用已有框架和 `/cmd_vel` 合约；不启动仿真执行插件。
真实雷达、底盘编码器/ESP32、平台、视觉、Dock 和健康汇总仍由对应模块负责人实现。
实机参数默认未标定；本次不将仿真参数标成硬件已验证。

## 完成与停止的判定

- 举起：平台到目标容差内、关节速度很小并连续稳定；货架实际高度与平台几何一致，且当前货架已联接。
- 放下：关节到降下容差内并连续停稳；下一仿真步实测货架已落地，释放才完成。命令发布／请求超时都不算完成。
- 运动交接：导航保持未派发状态，等待接受请求之后的至少三帧新位姿/底盘反馈，并达到规定稳定时长。取消和失效数据均阻止派发。
- 故障停车：底盘和关节速度分别实测为零，状态新鲜，旧动作结束，停止服务成功。UNKNOWN 货物状态保持 UNKNOWN。
- 恢复限制：实测停车成功不等于故障解除；健康仍无效时进入 FAULT，不继续运动。

新 `robot/status` 字段 `base_motion_stopped`／`lift_motion_stopped` 必须由实测速度生成，
配合 `lift_state_source=measured`、新鲜 stamp 和 `stopped`。旧模块未提供独立测量字段时，
继续采用原 healthy＋stopped 停止契约。

ROS driver 和 Gazebo 插件分别有命令看门狗，丢失命令不会继续旧速度。
升降命令在动作期间丢失时保持当前实测位置，不自动降货；不以放宽超时解决数据失效。

## D 检查点前的规划／跟踪误差契约（2026-10-09）

本次依据为 `navigation/log/run_1009_205104_10636` 和保存的雷达地图
`runtime_logs/navigation/blocked_1791550477472475448.npz`：A/B/C 已完成，
空车前往 D 检查点时首先报 `current footprint blocked`，停车后的重试报起点包络被占据。
不是 D 货物举升或放下失败。

旧规划名义路线沿 y=0.390 通过，包含偏航余量的空车半宽为 0.084799m，
安全间距为 0.05m，包络上沿约为 0.524799m；D 架腿的占据格从 y=0.525000m 开始。
实际雷达位置 y=0.391327m 仍满足 0.012m 跟踪容差，但实际包络上沿约为 0.526126m，
因此撞上安全检查。规划和跟踪的容差原先没有统一，是这次故障的直接原因。

现在 `core.planner_for(..., for_tracking=True)` 为名义路径采用
`margin + position_tolerance`，模板即 5cm 安全间距 + 1.2cm 跟踪误差预留。
当前实测车体仍只检查 5cm 安全间距，避免将同一跟踪误差重复计入。
平移、载货和原地旋转都采用此区分；正常导航不删除占据格、不降低安全间距。
实机和联合模式共用此算法，硬件定位误差仍须标定并另行计入实际参数。

离线重放实际地图：旧路线为 (0.997,0.708)→(0.997,0.390)→(2.340,0.390)；
修正后路线为 (0.997,0.708)→(0.997,0.725)→(2.340,0.725)→(2.340,0.390)。
这段绕开架腿是完整安全包络所需。回归对每段施加 ±1.2cm 的两轴偏移后仍通过检查；
地图回归样本放在 `src/robot_navigation/test/data/d_approach_costmap.npz`，没有运行 ROS 节点。

本次评估 CSV 的 2942 个配对样本中，Gazebo 真值相邻采样的平移速度最大约 0.30m/s，
未发现离散位置跳变。采样间隔约为 0.1 仿真秒，不能据此排除采样之间异常或 GUI 卡顿。
已有零速度区间包含动作交接、拐点停稳、到位停稳、雷达观测分段和本次故障停车；
旧日志没有跟踪阶段及接收墙钟时间，不能准确归因所有停顿。

新增 `base/tracking_status.phase`（TRACKING／AXIS_STOP／SETTLING／COMPLETED／IDLE）
和 `segment_index`；评估 CSV／metrics 增加 `tracking_phase`、`odom_receive_wall_sec`、
`odom_receive_interval_wall_sec`、`odom_source_interval_sec`、`odom_receive_rtf`。
receive_rtf 是相邻位姿消息的源时间增量／本评估节点接收墙钟增量，
只能指示仿真变慢或消息成批到达，不能直接当成 GUI 帧率或端到端延迟。
ROS stamp 与墙钟时间不能直接相减。停止证据和任务成功判定没有被诊断字段替代。

当前离线验证：281 项 pytest、61 项导航 unittest 和一组 C++ 机构状态回归。
五包构建检查仍不等于本次修改后的 Gazebo 全流程验收；程序由操作者运行。


## 雷达地图变化的导航恢复契约（2026-10-09 第二次 D 运行）

`navigation/log/run_1009_211434_12051`：A/B/C 完成，空车前往 D 时，
在仿真时间约 200.5s 和 204.4s 两次报 `live radar route blocked`，
位置分别约 (1.000,0.680)、(1.000,0.446)，尚未到达 D。
上一处跟踪误差预留已生效；本次是后续地图更新后剩余路线不再有效。
旧日志没有阻断瞬间的地图，不能确定是哪一个格变化，也不能认定障碍位于车前或车后。

源代码原本仅在进入 NavigateToPose 时规划一次；途中任一段失效即取消并报告动作失败，
由状态机重试，两次就 FAULT。它还一直检查包括已走过段在内的整条路径。
实时雷达逐步揭示占据／未知边界时，这个失败处理不符合实时导航的恢复职责。

现在 RouteChanged 只表示当前实测包络与跟踪走廊仍有效、后续名义路线被新地图阻断。
导航器取消旧 TrackPath，如已经派发，则必须收到 terminal result 且 stopped=true。
未确认停车时设置故障并退出，禁止重规划；确认后继续等待接受后的新反馈停稳窗口，
再等待停车之后的新扫描，以及时间戳不早于该扫描的地图，才重新规划原目标。
取消、定位／地图失效、实际包络被占据、偏离走廊、货物状态变化均不会被此恢复捕获。
原导航总 deadline 不会刷新，实际无安全路线仍报告失败；不盲走、不自动报告到达。

剩余路径由同一 request_id 的 TrackPath segment_index 确定，索引必须单调且有效；
已完成段移除，当前段检查实测位姿在走廊内后，从其轴向投影点开始检查剩余扫掠。
车后出现新格不会因旧路径监测而阻断车前自由路线；当前位置安全检查始终保留。
出现阻断时保存完整 costmap NPZ，并在日志输出剩余路线、阻断原因、当前点与目标点。

离线回归覆盖连续三次地图变化仍保留同一目标和 deadline、取消后的测量停止确认、
未确认停车时禁止恢复、已完成／车后路段、新扫描与地图屏障、走廊偏离。
当前 289 项 pytest、61 项导航 unittest、一组 C++ 机构回归通过；五包构建检查通过。
没有由开发代理启动仿真；实际地图变化恢复和末尾全流程仍由操作者验收。
